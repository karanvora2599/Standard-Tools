13The audit trail

A call routed through dispatch() can write an immutable decision record: its inputs, the market data it pulled with content hashes, which execution path ran, and a hash of its output. That is enough to tell a stale or tampered cache from a genuine code change.

1 · CALL
A tool runs through dispatch() with validated inputs.
2 · RECORD
Inputs, data hashes, the path taken and the output hash go to the day's JSONL file.
3 · CHAIN
Each record hashes the one before it, across calendar days, so a deleted day is detected.
4 · ANCHOR
Optionally, an Ed25519 checkpoint signs a day's chain endpoint.
5 · REPLAY
sqt replay re-runs the call and says whether it still reproduces.

The sqt command

sqt replay <request_id>                # re-run it: do the data and the output still match?
sqt compare <id_a> <id_b>              # diff two records, field by field
sqt verify [--file PATH]               # check the hash chain, whole trail or one file
sqt anchor <date> --key PATH           # sign a checkpoint on a day's chain endpoint
sqt export --start D --end D --out F   # a date range, its manifest and a standalone verifier

Exit codes that mean something

sqt replay exits 0 when the output reproduced exactly, 1 on a confirmed mismatch, 2 when the record has no output hash to compare against, and 3 when it reproduced to twelve significant digits on a different native build or instruction-set path. sqt verify exits 0 when the chain is clean.

What it does and does not certify

It is an engineering control: tamper detection, not tamper prevention or regulatory certification. Checkpoint signing closes the one gap the chain cannot close alone, an internally consistent rewrite of a whole day. An exported bundle carries a dependency-free verifier for an auditor who does not install the package, and named input fields can be redacted to a salted, non-reversible hash before a record is written.

Both tiers have been through line-by-line audits. Most findings were not exotic: they were ordinary code that looked right, and the reason each survived review is usually more instructive than the fix.

Why parity tests were not enough

A test that pins only one backend cannot see the two disagree, which is how several divergences survived. The fixes are pinned by tests that hold the two backends against each other, and against a second oracle that neither of them shares.

15The testing regime

Nine layers, each catching a class of defect the others cannot. The rule underneath all of them: test against an answer known by construction, never against a recorded output.

What none of this establishes is that the numbers are useful. The regime checks that a statistic is computed correctly, refuses cleanly, reproduces exactly and is documented honestly. Whether a strategy makes money is not a property a test can assert.

16Performance, measured

The C++ extension is optional, and the API is identical either way. Every figure is measured by toggling the same module's HAS_CPP flag and timing both paths back to back, and the ports that did not pay off are reported with the ones that did.

An extension built from other C++ sources than the ones beside the package is refused at import, with a warning naming the file and the command that rebuilds it, so it cannot answer with old kernels.

Where it pays

Rolling Hurst at 274×. A 2,000-name cointegration scan, both orders of all 1,999,000 pairs, in 1.7 minutes at 500 bars. The backtest kernel at about 58×, once a wrapper-redundancy bug that had held it at 1.0× end to end was found and fixed.

Where it ties

RSI, ADX and Wilder's ATR tie with the warm JIT-compiled Python path, and the GARCH recursion is slightly slower, at 0.8×. Those ports exist for the 200 ms to 1.1 s compile on the first call in a fresh process, which they remove, not for steady-state speed.
