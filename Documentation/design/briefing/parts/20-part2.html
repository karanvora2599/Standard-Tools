03System overview

One package, standard_quant_tools, importable from Python and served over MCP. Under its agent surface sit the same indicators, metrics, backtests, optimizers and models a person would call directly, and under the CPU-bound ones an optional C++ extension.

The five stages of a call

SERVEA client is given one runtime as MCP tools or function-calling schemas · under --tool-detail auto the heaviest schemas are thinned and describe_tool returns any of them in full
DISPATCHThe input is validated against the tool's Pydantic model · unknown arguments are refused · a tool from another runtime is unroutable, and the refusal names its owner
COMPUTEC++ kernels when the extension is built, the Python path when not, behind one API · sources declare when their facts became knowable · Sharpe is measured against a stated risk-free rate
HAND OFFEquity curves, trade logs, return panels and predictions are published as sqt:// references · their kind is checked when another runtime resolves them · nothing large passes through the conversation
RECORDA decision record per dispatched call: inputs, the content hashes of the data read, the execution path and a hash of the output, hash-chained across calendar days · sqt replay and sqt verify

From Python, a tool is one function call with a Pydantic model in and out. Over MCP, sqt-mcp --runtime research serves one runtime to any client.

04Twelve runtimes, enforced at dispatch

A runtime is an execution boundary, not a label. Each holds its own dispatch table, so a tool from another runtime cannot be called through it at all, and the refusal names the runtime that does own it.

That makes a scoping mistake recoverable and a hallucinated tool name obviously different from one. An agent serving research questions cannot run a backtest by accident, because the backtest runtime's tools are not in its table. A category narrows within a runtime (--categories microstructure is not the same as --runtime microstructure), and fifteen categories sit across the twelve.

Schema is the bare bytes of each runtime's tool schemas at full detail, as sqt-mcp --print-budget reports them. 217 of the 266 tools also sit in the analysis facade, get_agent_tools().

Why a boundary and not a filter

Narrowing the schemas a model is shown does not, by itself, stop a dispatcher from executing whatever name it is handed: a model shown two research tools that names a backtest would still get a backtest. Here the narrowing and the execution are the same table: scope is enforced where the call runs, so what an agent was not given it cannot do. Registering a tool touches six places (the function, its input and result models, the runtime's definitions and dispatch, and the facade), and a whole-surface test (section 15) fails when one is missed.

05Typed references between runtimes

Runtimes isolate execution, not data. Every real workflow spans them: screen in research, backtest in backtest, size in portfolio, hand a model's predictions to an allocation. Bulk values cross as typed references.

sqt://<kind>/<run_id>/<name>

A producer publishes a bulk value under a run_id and gets back a string. Any consumer in any runtime resolves it. Neither side knows the other exists, so N producers and M consumers need N + M integrations instead of N × M bespoke bridges, and nothing is transcribed through a context window on the way.

handoff.resolve(ref, expect="equity_curve")
# ValidationError: expected an 'equity_curve' reference but
# 'sqt://trade_log/run1/trades' is a 'trade_log'. ...
The kind is checked on resolve

A consumer states the kind it expects. Handing a trade log to a tool that wants an equity curve fails with an error naming both kinds, instead of producing a drawdown computed from the wrong series.

References are tools too

describe_reference, read_reference, convert_reference and list_reference_kinds live in the meta runtime, so any agent can inspect what it was handed.

06The MCP server and the context budget

The 266 tools cost about 727 KB of schema, roughly 186,000 tokens, held for a whole session. That is the constraint the server is designed around, so what to serve is the first decision rather than a tuning knob.

At full detail a tool averages 3,132 bytes over the wire. A session ceiling of 180,000 bytes, which the server once had, buys about 57 tools; taken smallest first, only 127 of the 266 fit. No amount of schema-shrinking brings the whole surface back, which is why a client is served one runtime, and why --runtime all is a diagnostic rather than a deployment. There is no fixed ceiling now: what a client can afford is a property of the client.

Thinning, with the full schema one call away

--tool-detail auto is the default. It thins the most expensive schemas until a runtime fits, and injects describe_tool, which returns any thinned schema in full. Served sizes under auto:

What a session holds

  • The default session serves four categories (screening, analysis, quantitative research and discovery): 62 tools, about 23,000 tokens of schema.
  • Resources expose sqt:// references, and prompts package common workflows.
  • Long-running tools, run_backtest_optimization and scan_pairs, are served only with --enable-long-running.
  • The audit trail covers calls made over the protocol, through the same dispatch as calls made from Python.

Served bytes are the envelope the server sends; the table in section 04 is bare schema bytes. The two are different instruments and are not comparable line for line.
