# Survey: `delta_one/`, `indicators/`, `metrics/` — implemented vs. exposed

Slice: `src/standard_quant_tools/delta_one/` (17 files, 4,553 lines), `src/standard_quant_tools/indicators/` (6 files, 1,186 lines), `src/standard_quant_tools/metrics/` (5 files, 1,229 lines). 6,965 lines total.

Tool surface checked: `agent/runtimes/{research,backtest,portfolio,data,meta,derivatives,delta_one}/tools.py`, `agent/runtimes/research/{reference_tools,diagnostic_tools}.py`, `agent/runtimes/backtest/futures_tools.py`, `agent/runtimes/microstructure/*_tools.py`, `modeling/agent/{tools,feature_tools,dataset_tools}.py`, `modeling/features/*.py` (feature registry), and `Documentation/20_tool_index.md` (211 tools). Every "exposed by" claim below is from a grep of the import and the call site, not from the tool description.

## 1. Summary

| | Count |
|---|---|
| Public functions / classes inventoried | **66** (72 counting `ContractSpec`'s six methods separately) |
| Reached DIRECTLY by at least one tool (imported and called from a tools file) | **57** |
| Reached only INDIRECTLY (called by an exposed library function, never by a tool) | **7** — `forward_price`, `observed_carry_rate`, `to_date`, `year_fraction`, `tracking_error`, `annualized_sharpe`, `has_no_dispersion` |
| Not reached by any tool, directly or indirectly | **2** — `ContractSpec` (and its 6 methods), `day_count` |
| Constant tables (SOLVE_TARGETS, EXPRESSION_KINDS, HEDGE_OBJECTIVES, CHANNELS, CHANNEL_USES, QUOTE_CONVENTIONS, CONVENTIONS, SETTLEMENT_TYPES) | 8, all surfaced only as prose inside result `meaning`/`warnings` fields or hard-coded `Literal[...]` in input models |

The function-name view understates the gap. The real unexposed capability in this slice is mostly **computed-then-discarded output** and **fetch-only entry points**:

- `trade_excursions` computes per-trade MAE/MFE; the only tool surfaces two averages.
- `parkinson/garman_klass/yang_zhang_volatility` produce a full rolling series; the only tool returns the last value, for a ticker only.
- `evt_tail_risk`, `treynor_ratio`, `information_ratio` are reachable only through symbol-fetching tools; `calculate_series_metrics` (the "any series" tool) does not list them.
- `drawdown_periods` and `trade_expectancy` run only inside a backtest re-run or on a persisted equity artifact; neither takes a supplied series.
- `day_count` / `year_fraction` / `CONVENTIONS` exist so that a $27,500 ACT/360-vs-ACT/365F gap on $100m is computable; no tool lets an agent compute it.
- `ContractSpec` turns (price, multiplier, tick) into money and ticks into currency; `analyze_roll` and `size_futures_hedge` ask the agent for `multiplier` and `tick_value` as raw floats instead.

## 6. Unexposed / under-exposed capability, by theme

### A. Contract and day-count arithmetic (delta_one) — no route at all
- `ContractSpec.tick_value`, `.notional`, `.contracts_for`, `.time_to_expiry`, `.from_mapping` — contract economics from a spec. `size_futures_hedge` re-derives `contract_notional = f*m` itself; `analyze_roll` asks for `tick_value` as a bare float and `days_between_expiries` as a bare float that the agent must compute from two expiry dates by hand.
- `day_count`, `year_fraction`, `CONVENTIONS` — the ACT/360 vs ACT/365F vs 30/360 vs ACT/ACT accrual. Reachable only implicitly by passing dates to `price_total_return_swap`. The library's own docstring quantifies the stake ("about $27,500 on $100m at 4%") and no tool can produce that number.

### B. Computed then discarded (metrics)
- `trade_excursions` per-trade `mae_pct` / `mfe_pct` — only two means reach the agent. The distribution (what fraction of eventual winners first went 2% against; what MFE was left on the table) is the input to every stop/target decision and is thrown away.
- `drawdown_periods` full table — only via a persisted equity URI (`get_drawdown_table`) or by re-running a built-in strategy (`get_backtest_diagnostics`). Not on a supplied returns/equity `DataSource`.
- `trade_expectancy` — only by re-running a built-in strategy. No tool reads a persisted `sqt://trade_log/...` artifact for it, although `get_drawdown_table` exists precisely to avoid the re-run for equity curves.
- `parkinson/garman_klass/yang_zhang_volatility` — full rolling series computed; one scalar surfaced, ticker-only.

### C. "Any series" gaps (metrics)
`calculate_series_metrics` is the one tool that takes a `DataSource` (symbol | `sqt://` ref | inline values). Its closed `_METRICS` registry omits `information_ratio`, `treynor_ratio`, `evt_tail_risk`, `drawdown_periods`/`top_n_drawdowns`, and exposes no `confidence` for `var_*`/`cvar`. So a model's out-of-sample return series can get a Sharpe but not an IR, a Treynor, or an EVT tail.

### D. Quote-to-rate translation (delta_one)
`compare_expressions` needs every row pre-translated into rates: the `future` row wants "basis over fair as financing", the `synthetic` row's `EXPRESSION_KINDS` text says "solve_carry on the parity forward is what produces the rate here" — but nothing in the function or its tool does that. The chain `observed_carry_rate` -> `solve_carry` -> row, and `total_return_future` -> row, exists in the library and the agent has to run three or four tools and hand-copy numbers between them.

### E. Evaluation of a SUPPLIED basket (delta_one)
`tracking_error` (standalone) is unexposed. `optimize_replication_basket` fits weights; there is no tool that scores weights the desk already holds against a benchmark (TE, IR, beta, rolling TE, active drawdown), which is the question asked every rebalance.

### F. Indicator parameters (research)
`get_technical_analysis` hard-codes `rsi(close, 14)`, `macd(close)`, `bollinger_bands(close)`, `atr(...)`, `adx(...)`, `williams_r(...)` at defaults; only SMA/EMA period lists are inputs. `get_technical_panel` already exposes `rsi_period`, `adx_period`, `atr_period`, `bollinger_period`, `bollinger_num_std`, `stoch_*`. Parameter asymmetry between two tools computing the same indicators.

## 7. Proposed new tools

Ordering is by expected value to an agent; effort is S (<1 day: input/result models + thin wrapper), M (1–3 days: new composition logic + tests), L (>3 days or needs a library change).

### 7.1 `analyze_trade_log` — backtest runtime — **M**
- **Inputs:** `trade_log_uri` (`sqt://trade_log/...`, the artifact `run_backtest_compact`/`get_backtest_diagnostics` can persist) OR `symbol`+`strategy_type`+`parameters` (re-run, as today); optional `price_panel_ref` for MAE/MFE; `stop_grid_pct: List[float]` (e.g. 0.5..5), `target_grid_pct: List[float]`; `min_trades=20`.
- **Outputs:** `trade_expectancy` block (expectancy, avg winner/loser, payoff, streaks, win/loss/flat counts); MAE/MFE percentiles (p10/p25/p50/p75/p90) split by winners vs losers; `mfe_capture` = median(return_pct / mfe_pct) for winners; a stop sweep table: for each candidate stop, how many losers it would have cut and how many eventual winners it would have stopped out (from per-trade MAE); a target sweep from MFE; `recommended_stop_range` only if the losers' MAE distribution separates from the winners' (report the overlap, do not pick a point).
- **Backing:** `metrics.diagnostics.trade_expectancy`, `trade_excursions`, `exposure_stats`; `backtest` artifact loader already used by `get_drawdown_table`.
- **Why a decision:** "Where should the stop be, and is my exit leaving money on the table" is the question a trade log exists to answer; the library already computes the per-trade numbers and discards them. This is the trade-log twin of `get_drawdown_table`, which was added for exactly the re-run-vs-artifact reason stated in its docstring.
- **Warnings the tool must carry:** (1) In-sample: the trades were produced by the strategy's own exits, so MFE is censored by those exits and a target sweep is optimistic. (2) MAE/MFE are measured against the weighted-average cost basis, not a fill price (docstring of `trade_excursions`), so a lot that scaled in reads a deeper MAE than any fill saw. (3) A daily bar's High and Low have no known order: a stop and a target both inside one bar are ambiguous and the sweep must count them as "undetermined", not as hits. (4) Stop sweeps are a multiple-comparison exercise; with <~50 trades the best stop is noise, so report the count behind every cell. (5) Fewer than `min_trades` -> refuse the sweep, still return expectancy.

### 7.2 `compare_expressions_from_quotes` — delta_one runtime — **M**
- **Inputs:** `spot`, `risk_free_rate`, `dividend_yield`, `borrow_rate`, `notional`, `horizon_years`, `direction`; optional quote blocks: `future {price, time_to_expiry, multiplier?, spread_ticks?, tick_value?, rolls_per_year?}`, `trf {quote, quote_convention, time_to_expiry, reference_rate}`, `swap {reference_rate, spread_bps, day_count}`, `etf {expense_ratio, spread_bps, dividend_withholding_pct?}`, `synthetic {call, put, strike, time_to_expiry}` (parity forward via `analysis.derivatives`), `cash {financing_rate, spread_bps}`. Every block is optional; only supplied ones become rows.
- **Outputs:** the `compare_expressions` ranking plus a `derivation` per row: which quote produced which rate (e.g. `future.financing_rate = solve_carry(...).solved_rate` with the assumed dividend/borrow), so the agent can see that the future row's "financing" is a conditional implied rate and not a quote.
- **Backing:** `carry.solve_carry`, `carry.observed_carry_rate`, `swaps.total_return_future`, `expressions.compare_expressions`, `analysis.derivatives.implied_forward_price` / put-call parity (already exposed in `derivatives`).
- **Why a decision:** "Given these live quotes, which is the cheapest way to hold $100m of SPX for six months" is the runtime's headline question (its module docstring says so); today it needs `solve_forward_carry` -> `analyze_total_return_future` -> hand-built expression rows -> `compare_delta_one_expressions`, with the sign convention (`borrow` is a receipt to a long) re-entered by the agent each time — the exact place `expressions.py` says sign errors come from.
- **Warnings:** every implied rate is CONDITIONAL on the supplied dividend/borrow (`solve_carry`'s own warning, propagated per row); execution terms default to zero so a row with `terms_supplied` of one is free by construction; the future row's roll cost is unknown unless `rolls_per_year`/`roll_cost_bps` are passed (existing warning); the synthetic row carries pin/early-exercise risk not priced here; costs only, not risk (existing warning).

### 7.3 `compare_tail_risk_models` — research runtime — **S/M**
- **Inputs:** `series: DataSource` (symbol | ref | values), `confidences: List[float]` (default [0.95, 0.99, 0.995]), `tail_fraction=0.05`, `method="pwm"`, `periods_per_year`.
- **Outputs:** per confidence: `var_historical`, `var_parametric`, `cvar`, `var_evt`, `cvar_evt`, `n_obs_backing_historical` (= n·(1−c), the count of observations at or beyond the empirical quantile), `evt_over_historical` ratio, and the GPD fit (`shape_xi`, `tail_classification`, `n_exceedances`); a one-line `sizing_basis` recommendation: "historical" when n·(1−c) >= 20, "evt" when historical is backed by fewer than ~5 observations and the GPD fit is valid, "insufficient" otherwise.
- **Backing:** `var_historical`, `var_parametric`, `cvar`, `evt_tail_risk`.
- **Why a decision:** "Which VaR do I size on at 99.5% with 500 days of history" is a choice between a quantile backed by two observations and a fitted extrapolation; `get_tail_risk_metrics` answers for one ticker at one confidence and `calculate_series_metrics` cannot run EVT at all. The tail-model choice is the decision; the four numbers side by side are how it is made.
- **Warnings:** all in-sample; `evt_tail_risk` refuses confidence <= 1−tail_fraction and <20 exceedances (surface the refusal per confidence, do not drop the row); GPD assumes i.i.d. exceedances, so vol clustering makes every figure optimistic in a stress regime; parametric assumes Gaussian and is the number most likely to be wrong in the tail; threshold choice (`tail_fraction`) moves `xi` — report sensitivity at 0.05 and 0.10 or say it was not checked.

### 7.4 `evaluate_tracking_basket` — delta_one runtime — **S/M**
- **Inputs:** `returns: Dict[str, List[float]]` (candidates), `benchmark_returns: List[float]`, `weights: Dict[str, float]` (the basket actually held), `window=60`, `periods_per_year`, `compare_to_optimizer: bool=False` (+ `max_names`), `rebalance: Literal["daily","buy_and_hold"]="daily"`.
- **Outputs:** annualized `tracking_error`, `information_ratio`, `beta`, `correlation`, active return, max active drawdown, rolling TE (mean/min/max/last, sign of trend), names with the largest active-risk contribution, gross/net weight, and — if requested — the optimizer's TE for the same universe/cardinality as a reference point with the gap in bps.
- **Backing:** `hedging.tracking_error`, `risk_metrics.information_ratio`, `analysis.regression.calculate_beta`/`rolling_beta`, `risk_metrics.max_drawdown` on the active curve, `replication.optimize_replication_basket` (optional reference).
- **Why a decision:** "Is the basket I hold still tracking, and would re-optimizing be worth the turnover" — `optimize_replication_basket` only answers the second half and only for weights it chose. Supplied weights fitted on an earlier window make this an OUT-of-sample test, which the optimizer tool cannot give.
- **Warnings:** TE annualization assumes i.i.d. active returns; `rebalance="daily"` (returns-weighted) ignores drift of buy-and-hold weights — the two can differ by the basket's dispersion; an optimizer comparison is in-sample for the optimizer and out-of-sample for the held basket, so the gap flatters the optimizer; fewer than ~60 overlapping observations makes the rolling TE meaningless (refuse the rolling block, keep the full-sample one).

### 7.5 `compare_financing_accrual` — delta_one runtime — **S**
- **Inputs:** `notional`, `rate` (decimal), `spread_bps=0`, `start_date`, `end_date`, `conventions: List[str]` (default all four), optional `reference_convention` (what the confirmation says).
- **Outputs:** per convention: `days`, `denominator`, `year_fraction`, `accrued` (currency); pairwise gap vs the reference in currency and bps of notional; `largest_gap_currency`; a flag when any pair differs by more than a stated tolerance.
- **Backing:** `daycount.day_count`, `daycount.year_fraction`, `daycount.CONVENTIONS`.
- **Why a decision:** "Which convention is the counterparty using, and how much does a mismatch cost" is a check a desk does on every swap confirmation and financing invoice; the library's own docstring computes it by hand as the justification for the module. `day_count` returning the (numerator, denominator) pair exists precisely so a surprising number can be attributed to the date or to the convention — that attribution is the output.
- **Warnings:** calendar days only — no holiday calendar, no business-day roll (Following/Modified Following), so a period ending on a weekend is used as given; 30E/360 is not supported and is not the same as 30/360; ACT/ACT's denominator is an effective one (days / fraction) and does not reproduce a textbook single-year figure across a year boundary; not a substitute for the confirmation's own schedule when the notional resets.

### 7.6 `diagnose_volatility_source` — research runtime — **S** (S with a caveat; M if the library adds YZ components)
- **Inputs:** `ohlcv: DataSource` (symbol | `sqt://ohlcv` ref), `period=20`, `periods_per_year`, `history_window=252`.
- **Outputs:** current close-to-close, Parkinson, Garman-Klass, Yang-Zhang; each one's percentile inside `history_window`; ratios: `yang_zhang / garman_klass` (overnight-gap share, since YZ is the only one that includes close-to-open), `parkinson / close_to_close` (intraday range vs close-to-close moves), `garman_klass / parkinson`; a `regime` label: "gap-driven", "range-driven", "close-driven", "consistent"; the number of bars with `high==low` or missing Open (which silently zero the range terms).
- **Backing:** `parkinson_volatility`, `garman_klass_volatility`, `yang_zhang_volatility`, `annualized_volatility`.
- **Why a decision:** "Is the realized vol coming from overnight gaps or intraday range" decides hedge frequency (intraday vs close-to-close delta hedging), whether gamma P&L accrues when the market is closed, and whether the option cone (`get_volatility_cone`) is comparing implied against the right realized number. `get_volatility_estimators` returns the four numbers for one ticker and no history, and only the YZ/close ratio.
- **Warnings:** Parkinson and Garman-Klass assume zero drift and no jumps and are biased low on a trending or gapping name — the ratios are diagnostic, not a decomposition; `yang_zhang_volatility` does not return its three components, so "overnight share" is inferred from YZ−GK, not measured (a library change returning `var_overnight`, `var_open_close`, `mean_rs` would make it measured — flag as a follow-up); a daily bar's Open is the auction print, so "overnight" includes the opening auction; all windows are trailing and annualized with a fixed `periods_per_year` that is only right for daily bars (the feature registry already refuses intraday intervals for this reason).

### 7.7 (lower priority) `get_drawdown_episodes` on a `DataSource` — research or backtest — **S**
- Rather than a new tool, prefer §8.2 below (give `get_drawdown_table` a `DataSource`). Listed here only because two tools already answer this question with two start conventions (`get_drawdown_table` = peak bar; `get_drawdown_profile` = first underwater bar), and a third would make it worse. If anything is built, it should be one tool with a `start_convention` parameter and both implementations retired to one.

## 9. Dead code, duplication, docstring-vs-code

1. **`hedging.hedge_effectiveness` reports a `tracking_error` that is identical to `volatility_after`.** `te = std(unhedged − (−ratio)·hedge)·√ppy` = `std(unhedged + ratio·hedge)·√ppy` = `vol_after`. The result model (`HedgeEffectivenessResult.tracking_error`, described as "Annualized active-return sigma") presents it as a distinct statistic. It also does not call the module's own `tracking_error()` two functions above it. Either drop the field or define it as TE of the hedged book vs zero-return (which is what it is) and say so.
2. **`baskets.index_basket` `missing_symbols` is always `[]`.** `_parse_constituents` raises on a missing `price`, so the later `[row for row in rows if row.get("price") is None]` can never match. Dead field in the result and in `IndexBasketResult`.
3. **`scan.basis_scan` docstring promises an optional `multiplier` per pair; the code never reads it**, and `BasisScanPair` (extra="forbid") has no such field, so a caller who follows the docstring is refused at the schema.
4. **Two drawdown-episode implementations with two start conventions, both exposed:** `metrics.diagnostics.drawdown_periods` (start = peak bar; `get_drawdown_table`, `get_backtest_diagnostics`) and `analysis.diagnostics.drawdown_profile` (start = first bar underwater; `get_drawdown_profile`). Both result models are named `DrawdownEpisode`. The `drawdown_periods` docstring documents the split and pins it with a test; it remains a duplication an agent can hit from two tools with different answers for "start".
5. **The name "atr" means two things across two tools.** `indicators.volatility.atr` is a SIMPLE rolling mean of true range and is what `get_technical_analysis` and `get_position_size` return as "atr"; `indicators.panel.technical_indicators_panel` (and therefore `get_technical_panel`, `compute_indicator_panel`) computes "atr" with `wilder_atr`. `research/tools.py:160-164` acknowledges this and excludes "atr" from its fused path for that reason, but the two tools still emit the same key for different numbers.
6. **`technical_indicators_panel` is wrapped by two tools** (`get_technical_panel` in `research/tools.py`, `compute_indicator_panel` in `research/reference_tools.py`). The rationale (one returns the latest bar inline, one publishes refs and accepts a `price_panel_ref`) is documented, but the parameter sets differ (`compute_indicator_panel` exposes no periods) and a model has two names for one computation.
7. **`information_ratio` still computes tracking error inline** (`active.std()*sqrt(ppy)`) while `hedging.tracking_error` was written to be "the denominator ... inspected on its own" and says it "was a local variable inside information_ratio". The consolidation its docstring describes did not happen; the two are the same formula in two files.
8. **`volume.vwap(period=None)` is documented as a "cumulative session VWAP"** but `get_technical_analysis` calls it on a multi-year daily frame, so the reported `vwap` is the volume-weighted average since the query's `start_date`, anchored to an arbitrary date. The tool does not say so.
9. **`expressions.EXPRESSION_KINDS["synthetic"]` says "solve_carry on the parity forward is what produces the rate here"** — nothing in `compare_expressions` or its tool does that; the caller must. Promise exceeds the code (7.2 would make it true).
10. **`streaming.reset_spread_monitor` does not clear `degenerate_n` / `degenerate_mean` / `degenerate_m2`.** A full reset (`keep_baseline=False`) relearns `n`, `mean`, `m2` and the baseline, but `_refreeze_if_possible` seeds from `state.get("degenerate_n", 0)` etc., so if the SECOND warm-up is also degenerate the re-freeze continues from the previous life's accumulators. Latent state-carry bug, not dead code.
11. **Unused imports across `delta_one/`:** every module does `from ._numbers import bounded, finite, non_negative, positive` and most use two of the four (24 unused names across 12 modules; `hedging.py` even imports `positive` unused). `basis.py` and `futures.py` import `_positive` from `analysis.derivatives` and never call it. `basis.basis_history` also shadows the imported `finite` with a local `finite = target.dropna()`. Harmless at runtime; lint noise that hides real drift.
12. **`daycount.day_count` has no library caller** for its own sake (`year_fraction` calls it for three conventions and bypasses it for ACT/ACT); `daycount.TRADING_DAYS_PER_YEAR` is re-exported "so the eighth copy is not written" but every importer still takes it from `constants`. `CONVENTIONS` keys are re-typed as a `Literal` in `TotalReturnSwapInput.day_count` rather than derived, so adding a convention needs two edits.
13. **`ContractSpec.contracts_for`** duplicates the `exposure / (price·multiplier)` arithmetic that `futures_hedge` re-derives inline (`contract_notional = f*m; exact = -dollar_beta/exposure_per_contract`). One of them should be the other.
14. **`carry.forward_price`** is a pure pass-through to `implied_forward_price` with one internal caller (`cash_futures_basis`). Documented as deliberate; not dead, but a third name for one equation once `get_implied_forward` is counted.
15. **`trade_excursions` per-trade columns are computed and discarded** by the only tool that calls it (`get_backtest_diagnostics` keeps `mean()` of each). Not dead code — dead output.
16. **`metrics/__init__.py` does not export `has_no_dispersion` or `annualized_sharpe`** even though `risk_metrics` positions them as the consolidation point that `analysis.diagnostics`, `backtesting.overfitting`, `backtesting.trade_analysis`, `analysis.inference`, `analysis.liquidity_events` and `backtest.engine` import from; each imports from `metrics.risk_metrics` directly. Minor.
17. **`momentum.stochastic_oscillator` and `volatility.bollinger_bands` catch `Exception` on the C++ path** and fall back silently to pandas with a `logger.warning`. Input validation is done before the try (commented), so this is safe, but a kernel bug would be invisible to the tool result.
